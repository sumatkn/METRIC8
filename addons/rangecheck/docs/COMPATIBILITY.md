# Forever client compatibility and validation

Reviewed November 21, 2026 under [P-004](../../../docs/PROCEDURES.md#p-004-forever-compatibility-review).

- **Live build and interface.** Blizzard's `wowf` version feed and the local install metadata both reported 1.60.1.71037. The installed Forever client's engine survey patch and installed add-on manifests corroborated interface 16001. An addon author also independently recorded 16001 from the in-game `GetBuildInfo()` query. The manifest uses 16001 and the Forever game type, `camelot`. [Blizzard version feed](https://us.version.battle.net/wowf/versions) · [In-game interface report](https://github.com/Karl-HeinzSchneider/WoW-BetterGroupLoot/blob/main/REWORK_NOTES.md)
- **Export and hotfixes.** The Forever UI export head was 71037, the same build reviewed for the November 20 suite baseline. The export diff from 70959 to 71037 changed generated Battle.net docs and several Blizzard UI modules, including the target frame, without changing the spell, spellbook, unit, or item API definitions used here. Blizzard's November 20 hotfix list contained no addon range API changes. An addon author's Auto Shot implementation supports the general probe choice, and reports approximate boundaries for separate minimum-distance checks. Neither the report nor the export establishes behavior in all combat contexts. [71037 export diff](https://github.com/Gethe/wow-ui-source/commit/734f065329cff4992835b01a84f210a297db91b6) · [Blizzard hotfixes](https://worldofwarcraft.blizzard.com/en-us/news/24315281/wow-forever-hotfixes-november-20-2026) · [Hunter addon author's notes](https://github.com/matejkadlec/forever-addons)
- **Range.lua.** `UnitClass` uses the player class token. `UnitExists`, `UnitCanAttack` and `UnitIsDeadOrGhost` gate the target. `C_Spell.GetSpellName` resolves the setup ID to a localized name; the spellbook lookup filters hidden, future, off-spec and flyout entries and reads the player slot's returned spell ID. `C_Spell.IsSpellInRange` returns true, false or nil. Nil, unexpected values, secret values and call failures are handled as unavailable. A false result is used for OUT only when the spell's reported minimum is zero and all other applicable checks were also interpretable negatives. The native check handles current spell mechanics when the client exposes them. No hardcoded yardage or talent modifiers are used. The ranged equipment gate checks the ranged inventory slot and the item class/subclass from `C_Item.GetItemInfoInstant`. [Spell definitions](https://github.com/Gethe/wow-ui-source/blob/734f065329cff4992835b01a84f210a297db91b6/Interface/AddOns/Blizzard_APIDocumentationGenerated/SpellDocumentation.lua) · [Spellbook definitions](https://github.com/Gethe/wow-ui-source/blob/734f065329cff4992835b01a84f210a297db91b6/Interface/AddOns/Blizzard_APIDocumentationGenerated/SpellBookDocumentation.lua) · [Unit definitions](https://github.com/Gethe/wow-ui-source/blob/734f065329cff4992835b01a84f210a297db91b6/Interface/AddOns/Blizzard_APIDocumentationGenerated/UnitDocumentation.lua) · [Item definitions](https://github.com/Gethe/wow-ui-source/blob/734f065329cff4992835b01a84f210a297db91b6/Interface/AddOns/Blizzard_APIDocumentationGenerated/ItemDocumentation.lua)
- **Load order and persistence.** The TOC loads the Lua 5.1-compatible modules in dependency order. `PLAYER_LOGIN` initializes settings and starts updates. The icon uses a regular frame, textures and a font string. Profile storage uses account-wide `METRIC8_RangeCheckDB` for global and class options and `METRIC8_RangeCheckCharacterDB` for native per-character storage. No realm name or identifier is required. External theme addons can use the TOC dependency and registration function, with no module loader or library dependency.

## Validation performed

A local Lua 5.2 mock loaded all files in TOC order and exercised startup, periodic updates, no target, invalid targets, spell ranks, melee/ranged/spell/wand priority, equipment changes, nil/secret/error cases, ambiguous Hunter negatives, theme registration and precedence, scaling, drag position, and profile inheritance. The mock does not establish runtime behavior in WoW. The third-party simulator could not initialize and provided no validation.

## Hunter follow-up (0.1.1-dev)

The maintainer saw a ranged indication on a Hunter and reported difficulty distinguishing melee and the dead zone. A Forever addon author reported that Raptor Strike can answer in range well outside melee reach, while Wing Clip changes its answer at melee reach. This revision uses Wing Clip once learned and retains the existing Auto Shot check. It also makes no target, a nonattackable target and an unavailable range visibly distinct. No new client APIs were added. This revision was reviewed against source and reported behavior. Gameplay verification is pending with the maintainer. [Forever range probe observations](https://github.com/Nedyar/NameplateDistance/blob/main/Range.lua#L103)

## Line-of-sight and melee feedback (0.1.2-dev)

RangeCheck listens to `UI_ERROR_MESSAGE` and recognizes the client's localized line-of-sight error text. The event supplies an error and has no unit argument. The corner badge reports a recent error for two seconds and clears when the target changes. The client export did not expose a continuous target line-of-sight query. A quiet auto-attack cannot establish why no damage occurred. Forever addon authors also report that passive range reads for Attack (6603) and next-swing attacks can give false positives, so the Hunter melee probe remains Wing Clip. The reported X does not match a bundled 0.1.1 label; `/rangecheck status` reports the loaded version, computed status and probe results for follow-up. Source review only for this revision. [Forever melee observations](https://github.com/wealdly/JustAC/blob/main/BlizzardAPI/StateHelpers.lua)

In 0.1.3-dev, `/rangecheck debug on` prints one initial snapshot and prints again when the target or normalized probe results change. It reports the melee and ranged probes even if one has already confirmed range. Initial and changed line-of-sight errors are reported separately while repeats inside the badge window are suppressed. No further API changes were needed.

## Action-bar range and distance (0.1.4-dev)

The maintainer’s 0.1.3-dev debug log repeatedly showed Wing Clip as unavailable on living attackable targets, while Auto Shot returned true at range. The log also observed line-of-sight errors while the icon reported ranged. The client exposes `C_ActionBar.FindSpellActionButtons`, `HasRangeRequirements` and `IsActionInRange`. RangeCheck uses these read-only APIs for Wing Clip if slotted. This reads the same kind of range signal used by the action button, without inspecting color or activating the spell. `UnitDistanceSquared` is used only when checkedDistance is true and the number is readable. Where distance is unavailable, a positive spell result with nonzero, readable range metadata supports an approximate band. Melee reach and hitboxes can prevent a numeric estimate. The live line-of-sight query remains unavailable in the reviewed API. The action error badge is higher contrast and remains visible for three seconds. [Action-bar API](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/ActionBarFrameDocumentation.lua) · [Unit API](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/UnitDocumentation.lua)

## Hunter main-hand range (0.1.5-dev)

Hunter melee uses the read-only `C_SwingTimer.IsTargetWithinSwingRange(Enum.PlayerSwingType.MainHand)` API. The Forever export specifies a nullable boolean. RangeCheck preserves false and treats nil, restricted and unreadable responses as unavailable. It neither enables a shared range-check flag nor activates auto-attack. Beta and newer addon-author reports differ on when this query is readable. The maintainer can inspect the native result in debug mode without training or placing a melee ability. [Forever SwingTimer API](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/SwingTimerDocumentation.lua) · [Beta observations](https://github.com/Thunderz96/forever-addon-kit) · [SwedgeTimer implementation notes](https://github.com/ssdeanx/SwedgeTimer)

## Blizzard UI investigation (2026-11-21)

The built-in Forever swing timer enables the engine range check separately for each swing type, when the Auto-Attack Timer setting is enabled and that bar is configured for Always or In Combat. It then reads `IsTargetWithinSwingRange` on target changes and listens for `PLAYER_SWING_RANGE_UPDATE(swingType, isInRange, checksRange)`. The current RangeCheck build only reads the query and does not request the check. The maintainer's log showed nil on living, attackable targets, but did not establish whether Blizzard had enabled the check. A beta author reported nil and `checksRange=false` even after enabling it. An in-game comparison with Blizzard's main-hand timer enabled and set to Always can separate a missing registration from a result that remains unavailable. [Blizzard swing timer](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_SwingTimer/Blizzard_SwingTimer.lua#L372) · [Beta observations](https://github.com/Thunderz96/forever-addon-kit)

The timer's visual state collapses unchecked and in-range readings into the same non-dimmed presentation. Its visual state also suppresses the warning in Edit Mode and during an active swing. A hook on the color or dimming logic therefore cannot recover both positive and negative range outcomes. The default action bar uses per-slot `ACTION_RANGE_CHECK_UPDATE` and colors the hotkey red when the action was checked and is out of range. That is evidence about the slotted action only. It does not establish an independent melee limit or passive line of sight. [Blizzard action button](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_ActionBar/Shared/ActionButton.lua#L1201)

Even with explicit melee and ranged negatives, the ranged negative does not identify which Auto Shot boundary failed. A defensible dead-zone result needs a separate upper-bound observation placing the target below Auto Shot's minimum range. Fixed item checks can provide approximate bands where available. In-game observations on NPCs and the variable melee reach reported by addon authors do not justify presenting those bands as exact attack boundaries. No executable or in-game test was performed for this investigation. [Item API](https://github.com/Gethe/wow-ui-source/blob/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated/ItemDocumentation.lua) · [Measured range bands](https://www.curseforge.com/wow/addons/forever-rangefinder)

## In-game smoke test pending

1. Confirm `/dump GetBuildInfo()` and `/dump select(4, GetBuildInfo())`, then install from source and check login for Lua errors.
2. Try friendly, dead, hostile and cleared targets. Move toward and away from a hostile target with a learned preset ability, then repeat in combat. Check Hunter with and without a ranged weapon, and a wand caster with and without a wand. Verify ambiguity remains Unknown and try a Hunter with a range-enhancing talent.
3. Unlock and drag the icon, change scale, then reload. Switch class and character to check scope and apply a sample external theme in both presentation modes.

The proof of concept intentionally leaves Hunter dead-zone detection inactive. It needs a client-supported way to independently establish both the melee and the Auto Shot minimum-range boundaries.
