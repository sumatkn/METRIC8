# Rules of engagement

These rules implement the requested repository organization and the user's stated collaboration preferences. They do not imply approval of the optional workflows in [procedures](PROCEDURES.md).

## Scope and decisions

- Work on the requested component and keep changes proportional to the task.
- Separate presentation, functional behavior, and profile/configuration requirements where relevant.
- Ask for clarification when the missing answer materially affects scope or behavior; proceed with reversible organizational work when the task already authorizes it.
- Mark assumptions and recommendations explicitly. Record confirmed decisions separately from proposals.
- Do not expand requirements into implementation detail unless implementation is requested.

## Integrity and ownership

- Inspect existing files before changing them and preserve unrelated content.
- Keep original sources and derived outputs distinguishable.
- Identify imported material, its origin, and its applicable license.
- Keep each project self-contained in the repository unless a shared component is explicitly established.
- Never silently change visibility, licensing, or existing release files.

## Evidence and continuity

- Distinguish observed behavior, hypotheses, requirements, and untested claims.
- Record client/build information when compatibility is tested.
- Update suite memory for suite changes and project memory for project changes.
- Keep public working memory limited to technical context, decisions, blockers, and next steps.
- Use the current repository documents as the handoff source; resolve contradictions with the user.

## Delivery

Explain the resulting behavior or documentation change, relevant validation, and material limits. A scaffold is not an implemented feature; an untested archive is not a verified release.
